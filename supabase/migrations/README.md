# Database migrations

This directory holds the SQL migrations for the Recipe API database. The
directory is named `supabase/migrations/` for historical reasons — the
project originally ran on Supabase Cloud and adopted the Supabase CLI
filename convention. Migrations 28+ target a **self-hosted PostgreSQL 16**
instance on the VPS and the Supabase CLI is no longer in the loop.

We keep the directory name (and the existing filenames) stable so git
history, `git blame`, and external links continue to work.

## Apply order

Migrations are applied alphabetically. The naming convention is
`YYYYMMDDHHMMSS_short_name.sql`, e.g.

```
20251214000000_create_recipes_table.sql
20251214000001_create_crawl_jobs.sql
...
20260517000000_self_host_compat.sql
```

The in-house migrator (`recipe-api/src/scripts/migrate.ts`, built by Agent A)
walks this directory in sorted order, records every applied filename in a
`public.schema_migrations` table, and skips files that have already been run.
Each file is executed inside a single transaction so partial-apply failures
roll back cleanly.

```bash
# Apply any pending migrations against $DATABASE_URL:
DATABASE_URL=postgresql://recipe_app:<pw>@localhost:5432/recipe_base \
    npx ts-node recipe-api/src/scripts/migrate.ts
```

## The 5 originally-RLS-bound migrations

Five of the older migrations enabled Row Level Security and created policies
that referenced Supabase-managed roles (`anon`, `authenticated`,
`service_role`). On a vanilla Postgres install those roles do not exist and
RLS would silently deny all access. The compatibility layer
`20260517000000_self_host_compat.sql` neutralises every one of them:

| Original migration                                | Tables affected                                | Policies dropped                                                                                                  |
| ------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `20251214000000_create_recipes_table.sql`         | `recipes`                                      | `Enable read access for all users`, `Enable insert access for all users`, `Enable update access for all users`    |
| `20251214000001_create_crawl_jobs.sql`            | `crawl_jobs`                                   | same three names                                                                                                  |
| `20251214000008_ingredient_cache.sql`             | `ingredient_cache`                             | `Enable read access for all users`, `Enable insert for service role`, `Enable update for service role`            |
| `20251225000002_add_api_keys.sql`                 | `api_keys`                                     | `Service role only`                                                                                               |
| `20260511000001_off_products_table.sql`           | `off_products`                                 | `Public read`, `Service role write`                                                                               |
| `20260512200004_nutrition_source_tables.sql`      | `cnf_foods`, `frida_foods`, `ausnut_foods`     | `Public read`, `Service role write` on each                                                                       |

After dropping the policies, the compat layer:

1. Disables RLS on all 8 affected tables (`ALTER TABLE … DISABLE ROW LEVEL SECURITY`).
2. Revokes any leftover grants to `anon` / `authenticated` / `service_role`
   inside a `DO $$ … EXCEPTION WHEN undefined_object THEN NULL; END $$;`
   block (no-op if those roles never existed).
3. Grants `SELECT, INSERT, UPDATE, DELETE` to `recipe_app` and `SELECT` to
   `recipe_readonly`, plus `ALTER DEFAULT PRIVILEGES` so future migrations
   automatically grant correctly without re-running this file.

It also installs the `notify_crawl_job` / `notify_crawl_job_retry` triggers
(LISTEN/NOTIFY for the worker) and registers the two `pg_cron` jobs
(`refresh-recipe-stats`, `audit-pending-batch`).

## Adding a new migration

1. Pick a UTC timestamp greater than the most recent file in the directory.
   The conventional format is `YYYYMMDDHHMMSS` (14 digits), e.g.
   `20260603120000`. Generated by:

   ```bash
   date -u +%Y%m%d%H%M%S
   ```

2. Append a `_short_snake_case_name.sql` suffix that describes the change.
   Keep it short — the change should be obvious from the filename.

3. Write the migration. Prefer idempotent statements
   (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`,
   `CREATE OR REPLACE FUNCTION`, `ALTER TABLE … IF EXISTS`). For things
   without a built-in `IF NOT EXISTS` (policies, triggers, role grants),
   use:

   ```sql
   DO $$
   BEGIN
       <statement>;
   EXCEPTION WHEN duplicate_object THEN NULL;
   END $$;
   ```

4. **Do not** modify or re-order existing migration files. If you need to
   undo something, add a new migration that does the undo.

5. **Do not** create new RLS policies that reference `anon`,
   `authenticated`, or `service_role`. Those roles no longer exist.
   Grant directly to `recipe_app` / `recipe_readonly` instead.

6. Run the migrator locally against a scratch database before opening a PR.

## Running `psql -f` manually (emergencies)

If the migrator is broken or you need to apply a single file in a hurry,
you can run any migration directly:

```bash
PGPASSWORD=<recipe_owner_pw> psql \
    -h 127.0.0.1 -U recipe_owner -d recipe_base \
    -v ON_ERROR_STOP=1 \
    -f supabase/migrations/<file>.sql
```

If you do this, **manually insert a row into `schema_migrations`** so the
migrator doesn't re-run the file on its next pass:

```sql
INSERT INTO public.schema_migrations (filename, applied_at)
VALUES ('<file>.sql', now());
```

Use `recipe_owner` (not `recipe_app`) for emergency `psql -f` since most
DDL statements require ownership privileges.

## Do not use the Supabase CLI

The Supabase CLI (`supabase db push`, `supabase migration up`, etc.)
assumes the presence of Supabase-specific objects such as the `auth.users`
table, the `storage` schema, the `realtime` schema, `pgsodium`,
GoTrue/PostgREST configuration, and the `supabase_admin` role. Our
self-hosted Postgres has none of those. Running the CLI here will at best
fail noisily and at worst leave the database in a half-migrated state.

Use the in-house migrator (`recipe-api/src/scripts/migrate.ts`) for all
schema changes from this point on.
